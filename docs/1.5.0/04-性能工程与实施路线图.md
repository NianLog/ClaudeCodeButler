# CCB v1.5.0 性能工程与实施路线图

## 1. 原则

性能优化必须先有可复现 baseline。开发期间只报告测得的数据；没有启动应用或用户尚未人工验收时，不填写估算值代替测量。

## 2. 测量环境 contract

- production build，关闭 DevTools。
- 相同 Windows 版本、Node/Electron 版本、CPU power mode。
- 固定 fixture：配置文件数量、Claude project logs 大小、MCP/Agent/Skill 数量。
- cold start 每轮清理 app process，但不清空用户数据；运行 3 次取 median。
- memory 使用 main + renderer + utility processes 的 working set 总和，同时保留 per-process 数据。
- 记录 baseline commit、test commit、timestamp 和 raw JSON。

## 3. 指标

| ID | Metric | Collection point |
| --- | --- | --- |
| PERF-01 | process start -> renderer `did-finish-load` | main process timestamps |
| PERF-02 | renderer `navigationStart` -> app interactive | `performance.mark` |
| PERF-03 | idle working set after 60 s | Electron process metrics |
| PERF-04 | tray-hidden working set after 60 s | Electron process metrics |
| PERF-05 | idle CPU median over 60 s | process metrics sampling |
| PERF-06 | active watcher count | watcher registry instrumentation |
| PERF-07 | config scan duration and files visited | service telemetry |
| PERF-08 | main/preload/renderer bundle sizes | build artifact script |

性能数据只写入本地 `.ccb/performance/` 或 ignored artifacts，不采集 telemetry，不上传。

## 4. 优化顺序

### P0 — 测量与生命周期

1. 建立 performance marks 与本地 snapshot exporter。
2. service initialization 分为 `BOOT_CRITICAL`、`AFTER_RENDERER_READY`、`ON_DEMAND`。
3. adapter lifecycle：只有 enabled/detected tool 才能初始化 scan/watcher。

### P1 — Main process

1. 合并 app update/registry manifest check 的 HTTP、SemVer 和 cache infrastructure。
2. Config scan 改为 artifact paths 定向扫描，避免递归扫描无关目录。
3. watcher 按 artifact 去重，统一 debounce 和 dispose。
4. 大型 analytics/project JSONL 保持 streaming，并增加 cancellation/budget。

### P1 — Renderer

1. Tools/Registry/Analytics/Managed Mode 使用 route-level lazy chunks。
2. locales 拆分 feature namespace，避免 140 KB 单文件随首屏全部解析。
3. renderer 只保存 registry summaries；definition 详情按需查询。
4. 长列表统一 virtualization，避免重复 component trees。

### P2 — Storage

1. registry immutable snapshot cache。
2. config metadata index 使用 content hash/mtime 增量更新。
3. backup retention 和 log cleanup 在 idle task 执行。

## 5. 分阶段实施

### Phase 0：开发基线（已完成）

- Git baseline commit `42dff6d`。
- Semgrep 0 findings/errors；npm audit 0；65 tests；build/type-check passed。

### Foundation 静态构建记录（2026-07-12）

规则库 foundation 加入后的 production build 与 baseline build 对比：

| Artifact | Baseline | Foundation | 变化 |
| --- | ---: | ---: | ---: |
| Main bundle | 239.66 KB | 259.00 KB | +19.34 KB |
| Preload bundle | 11.29 KB | 11.86 KB | +0.57 KB |
| Settings lazy chunk | 28.01 KB | 30.95 KB | +2.94 KB |

这是 registry validator、storage、update service、IPC 与 Settings UI 的静态成本，不代表 runtime memory 或 startup performance。v1.5.0 后续必须通过 service lazy initialization、effective registry summary cache、feature locale split 等优化抵消新增成本，并以实机 snapshot 为准。

Generic detection/read-only discovery 完成后的 production build：main bundle `265.93 KB`、preload bundle `12.08 KB`、Settings lazy chunk `30.95 KB`；full suite 为 104 tests / 16 files。相对 foundation，main 增加 `6.93 KB`、preload 增加 `0.22 KB`，renderer Settings chunk 未增加。该数据仍仅代表静态 bundle size，不能宣称 runtime memory、CPU 或 startup time 已下降；实机性能验收继续留在 Phase 5。

Generic codec/edit/backup/restore foundation 完成后的 production build：main bundle `271.75 KB`、preload bundle `12.44 KB`、Settings lazy chunk `30.95 KB`、renderer entry `194.96 KB`；full suite 为 113 tests / 18 files。相对 read-only discovery 阶段，main 增加 `5.82 KB`、preload 增加 `0.36 KB`，Settings chunk 不变。新增成本位于 main/preload 权限边界，没有把 codec 或文件管理逻辑推入 renderer；它仍不是 runtime 资源下降证据。

### Phase 1：Registry core

- shared types、validator、embedded registry、atomic installed store、last-known-good。
- unit tests 覆盖 valid/invalid schema、limits、merge、rollback。

### Phase 2：Manifest/update integration

- main-only HTTP fetch、version check、explicit download/install。
- IPC 只暴露 status/check/install/rollback。
- UI 先接 Settings 内的 registry status，不建立 marketplace。

### Phase 3：Generic read-only tools

- tool list、detect、artifact discover/read。
- Claude adapter 与第二个 read-only adapter 验证 schema 通用性。

### Phase 4：Generic edit/backup

- format codecs、validation、atomic edit、backup/restore。
- Claude-specific activation 继续使用 bundled handler。

### Phase 5：Performance implementation

- 根据 baseline 优先修复 top contributors。
- 每项优化单独对比 raw samples，不把多项变化混成无法归因的结论。

### Phase 6：Migration and release

- 幂等数据 migration、compat facade、rollback rehearsal。
- 更新 README/CHANGELOG/运维与用户指南。

## 6. 每阶段门禁

- 上一阶段 tests/type-check/build/targeted lint 通过后才能进入下一阶段。
- 发现 bug 按 Cockroach Principle 搜索同类模式并一起修复。
- remote registry 在 Ed25519 signature 未落地前不得默认启用自动提示之外的网络能力。
- 任何性能优化不得通过关闭 validation、backup、安全检查或错误处理换取数字。

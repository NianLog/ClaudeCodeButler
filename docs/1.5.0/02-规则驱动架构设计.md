# CCB v1.5.0 规则驱动架构设计

## 1. 现状诊断

### 1.1 Claude-specific 耦合

- `ConfigType` 在 `src/shared/types.ts` 与 `src/shared/types/config.ts` 重复定义，且直接包含 `claude-*` variants。
- `path-manager` 暴露 `claudeDir`、`claudeJsonPath`、`claudeMdPath`、`claudeProjectsDir`。
- `config-service` 同时负责路径安全、扫描、格式判断、metadata、模板、backup、activate 和 migration，约 1376 行。
- `managed-mode-service` 约 1811 行并直接操作 `~/.claude/settings.json`。
- MCP、Agent、Skill、Project、Analytics、Version services 各自持有 `.claude` 路径假设。
- UI/locales/IPC/preload 都暴露 Claude-specific vocabulary。

### 1.2 性能结构风险

- main startup 同时初始化多个 domain service 和 file watcher。
- `ipc-handlers.ts`、`preload/index.ts`、locales 与大型 panels 持续增长，增加解析与维护成本。
- 未启用工具没有 adapter-level lifecycle，因此未来多工具会线性增加 watcher、scan 和 resident state。
- app update 在 main 和 renderer 各有一套 version parsing/network flow，适合在 v1.5.0 合并。

## 2. Target architecture

```text
Renderer (lazy feature modules)
        |
Typed IPC facade
        |
Application services
  ToolRegistryService        RegistryUpdateService
  ConfigArtifactService      PerformanceTelemetryService
        |
Domain contracts
  ToolDefinition -> ArtifactDefinition -> Capability
        |
Infrastructure adapters
  PathResolver  FormatCodec  Detector  AtomicStore  HTTP client
        |
Built-in registry + Installed registry + Last-known-good
```

## 3. Domain model

### ToolDefinition

描述一个 AI tool 的稳定身份、显示信息、platform support、detectors 和 artifacts。`toolId` 不包含版本号，也不作为文件路径直接使用，必须经过 safe segment validation。

### ConfigArtifactDefinition

描述一个可管理配置资产：format、platform paths、scope、capabilities、template、validation profile 和 sensitivity。一个 tool 可以有多个 artifact，例如 settings、instructions、MCP registry。

### Capability

使用 UPPERCASE enum，前后端与持久化保持一致：

- `DISCOVER`
- `READ`
- `VALIDATE`
- `EDIT`
- `BACKUP`
- `RESTORE`
- `ACTIVATE`
- `WATCH`

规则只能引用 capability；handler 由应用代码注册，例如 `JSON_FILE_V1`、`MARKDOWN_FILE_V1`、`CLAUDE_SETTINGS_ACTIVATION_V1`。unknown handler/capability 必须 fail closed。

## 4. Registry composition

```text
embedded registry (trusted, bundled)
          +
installed registry (verified, user-approved)
          =
effective registry (immutable snapshot)
```

合并规则：

1. embedded registry 提供最小可用 Claude adapter。
2. installed bundle 只有在 schema、compatibility、hash 和 policy 全部通过后参与合并。
3. 同 `toolId` 的 override 必须声明 `replacesVersion`，且 bundle version 不得低于 installed version，除非用户执行显式 rollback。
4. effective registry 生成 immutable snapshot；renderer 只获取 summary，需要详情时按 `toolId` 查询。

## 5. Path model

允许的 path variables：

- `${HOME}`
- `${APPDATA}`
- `${LOCALAPPDATA}`
- `${XDG_CONFIG_HOME}`
- `${CCB_DATA}`

禁止：environment variable arbitrary lookup、`..` traversal、UNC remote path、URL、glob recursive traversal。路径解析后必须匹配 artifact 声明的 allowed roots；写操作还需精确 capability authorization。

## 6. Format model

`format` 使用 UPPERCASE：`JSON`、`JSONC`、`YAML`、`TOML`、`MARKDOWN`、`TEXT`。每个 format 对应内置 codec。规则可以引用 validation profile，但 v1.5.0 不允许下载 arbitrary JSON Schema `$ref`；schema 必须内联、限制深度/节点数并禁止 remote refs，或引用 bundled profile。

## 7. Migration strategy

### Phase A: Strangler foundation

- 新增 shared registry types、validator、embedded Claude registry 和 atomic store。
- 现有 services 不改行为，先通过 facade 查询 Claude definition。

### Phase B: Generic read path

- 新增 generic tool/artifact list、detect 和 read IPC。
- renderer 新建 lazy-loaded “Tools” panel；现有 Claude panels 保留。

### Phase C: Generic write path

- 接入 validation、backup、edit；高风险 activate 仍走内置 Claude handler。
- `ConfigType` consumers 逐步迁到 `toolId/artifactId/format`。

### Phase D: Feature extraction

- MCP/Agent/Skill 从“Claude-only navigation”迁为 tool capabilities。
- Analytics 和 managed mode 保留 specialized feature module，不强行塞入通用 config CRUD。

## 8. 关键取舍

- 不采用 JSON Logic 或脚本语言：它们会把 registry 变为未审计执行环境。
- 不允许任意 regex：ReDoS 与跨 engine 行为不稳定；detector 使用 bounded literal/extension/magic-field predicates。
- 不一次性删除 Claude-specific facade：strangler migration 比 big-bang rewrite 更可验证。
- 不让 renderer 直接下载/安装：网络、hash、filesystem 和 rollback 都属于 main process authority。

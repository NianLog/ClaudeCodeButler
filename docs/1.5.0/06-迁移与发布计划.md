# CCB v1.5.0 迁移与发布计划

## 1. 发布原则

- v1.5.0 不执行不可逆的大爆炸迁移；旧 `.ccb/claude-configs` 保持兼容，通用 workspace layout 先以 facade 接入。
- 所有 migration 必须幂等、可重复运行、可回滚，并在修改用户数据前创建可验证备份。
- Remote registry 只有在正式 Ed25519 publisher public key 固定进 application binary 后才能从 preview 升级为 production。
- 性能结论必须来自用户在 production build 上执行的三轮实机样本，不使用静态 bundle size 代替 runtime 指标。

## 2. Release blockers

### R1 — Registry publisher identity

- [x] Manifest schema 要求 `signatureAlgorithm`、`keyId` 与 detached `signature`。
- [x] Main process 使用 pinned SPKI public key 验证 raw bundle bytes。
- [x] Signature 后继续验证 SHA-256、size、schema、registry version、minimum app version 与 downgrade policy。
- [x] 提供无网络的 offline signing helper，输出 manifest integrity/signature fields。
- [ ] 维护者离线生成并保管 Ed25519 private key，不提交 repository、不上传构建机。
- [ ] 将对应 SPKI public key 与稳定 `keyId` 写入 `REGISTRY_TRUSTED_PUBLIC_KEYS` 后重新打包。
- [ ] 使用 release candidate manifest/bundle 完成 valid、tampered、unknown-key 与 rollback rehearsal。

### R2 — Claude Code compatibility

- [x] 盘点 Config、MCP、Agent、Skill、Managed Mode 对 `.ccb/claude-configs` 的直接依赖。
- [x] 建立 legacy path compatibility facade，新增业务代码不再直接拼接旧目录。
- [ ] 验证现有配置 scan/edit/activate/backup 与 Managed Mode restore 无回归。
- [ ] v1.5.0 默认不移动旧数据；新 workspace 物理迁移延后，除非 rehearsal 证明可无损回滚。

实施记录：`ClaudeWorkspacePathFacade` 同时声明 legacy path 与 future workspace path，但 v1.5.0 默认固定为 `LEGACY_COMPAT`。路径选择不检查目录存在性、不自动创建 future workspace、不复制或移动用户文件；`ConfigService`、FileWatcher、菜单与 Managed Mode provider sync 统一消费 `pathManager.claudeConfigsDir` compatibility alias。

### R3 — Template ownership

- [x] user override 独立存储，registry update 不得覆盖。
- [x] 更新前展示 embedded/registry/user 三方 diff，并明确最终生效来源。

## 3. 推荐实施顺序

1. 维护者完成 offline signing key ceremony，并注入 public key。
2. 实施 legacy path compatibility facade，不进行物理目录迁移。
3. 完成 artifact-specific template ownership 与 diff preview。
4. 用户执行 performance baseline/acceptance，开发侧按数据做第二轮优化。
5. 完成 release candidate 安全、迁移、rollback、installer 与业务回归。

## 4. Automated preflight

开发期使用 `npm.cmd run release:preflight:preview`，允许空 publisher trust map但输出 warning。正式发布必须使用 `npm.cmd run release:preflight`；在 production public key 注入前该命令按设计失败，不能通过删除检查或传 preview 参数绕过。

三类 Windows 产物统一使用 `npm.cmd run pack:win:all` 生成；在 CA 与 publisher key 两项前置条件满足前，不重复执行已知会失败的 production packaging。

## 5. Rollback contract

- 应用 binary rollback 不删除或降级用户配置。
- Registry rollback 仅恢复 last-known-good bundle，不执行远程脚本或任意 migration。
- 数据格式发生变化时保留原文件 backup、migration journal 与版本 marker；失败必须恢复原路径。
- Release rehearsal 必须记录输入 fixture、执行版本、输出 hash、rollback 结果和人工验收结论。

## 6. 人工验收入口

自动化阶段已经止损在“代码、静态安全、构建与 contract 全部通过”的边界。剩余项涉及真实 publisher identity、企业证书环境、Electron runtime 与用户数据，只能由维护者按 [`09-手动验收清单.md`](./09-手动验收清单.md) 逐项执行并保存证据。

# CCB v1.5.0 手动验收清单

## 1. 适用范围与通过标准

本清单只覆盖自动化无法替代的真实发布环境、publisher identity、安装形态、用户数据、Electron runtime 与实机性能。自动化基线已经达到：Full Vitest `30 files / 188 tests`，Semgrep full `198 targets / 369 rules / 0 findings / 0 structured errors`，explicit-path `35 targets / 336 rules / 0 findings / 0 structured errors`；OSS fixpoint coverage limitation 已在安全报告披露；TypeScript、ESLint、root/proxy builds 与两套 npm audit 全部通过。

每项记录 `PASS / FAIL / BLOCKED`、时间、操作人、产物 hash/截图/日志路径。任一数据损坏、signature fail-open、跨 document navigation、未知 key 被接受或 production preflight 被绕过，均属于 release blocker，立即停止后续发布。

## 2. 验收前准备

1. 使用独立的 Windows 测试账号或可恢复虚拟机，固定 power mode、Windows build 与显示缩放。
2. 备份完整 `.ccb` 用户目录，尤其是 `.ccb/claude-configs`、`.ccb/backup`、`.ccb/registry`、`.ccb/performance` 与 `settings.json`。
3. 准备固定 fixture：至少 10 个 Claude configs、2 个 MCP servers、2 个 Agents、2 个 Skills、一份可识别 Codex config，以及足以触发统计/项目页面的本地记录。
4. 记录源码 commit、`node --version`、`npm --version`、Windows 版本和 Electron `40.10.6`。
5. 不要删除旧版本 binary；Installer、Portable 与 ZIP 分别使用隔离目录，避免互相覆盖。

## 3. 企业/代理 CA 与 Electron 下载

当前已知阻塞为 electron-builder 下载 Electron distribution 时报告 `unable to verify the first certificate`。必须建立正确证书信任链，禁止使用 `NODE_TLS_REJECT_UNAUTHORIZED=0` 或其他关闭 TLS verification 的方式。

### 3.1 配置 CA

1. 从组织管理员获取 PEM 格式、包含完整链的可信根/中间 CA，例如 `C:\certs\enterprise-ca.pem`，并通过组织提供的 fingerprint 核对文件。
2. 当前 PowerShell session 临时配置：

   ```powershell
   $env:NODE_EXTRA_CA_CERTS = 'C:\certs\enterprise-ca.pem'
   ```

3. 如果组织要求 npm 级配置，可改用：

   ```powershell
   npm.cmd config set cafile "C:\certs\enterprise-ca.pem"
   npm.cmd config get cafile
   ```

4. 运行 `npm.cmd run release:preflight:preview`。此时允许唯一 warning 为 production publisher trust map 尚未注入。
5. CA 配置完成后再运行 `npm.cmd run pack:win:all`。如果仍有 certificate error，记录完整错误和代理信息，停止验收，不降低 TLS 安全等级。

通过标准：Electron `40.10.6` distribution 能在 TLS verification 保持开启的情况下下载/复用，且 electron-builder 进入真实打包阶段。

## 4. Offline Ed25519 publisher key ceremony

该步骤应在断网的受控机器完成。Private key 不得进入 repository、普通开发机、CI、release artifact、日志或聊天记录；应用只固定 SPKI public key。

1. 在离线介质上的临时目录生成 Ed25519 keypair：

   ```powershell
   openssl genpkey -algorithm ED25519 -out registry-private-key-2026.pem
   openssl pkey -in registry-private-key-2026.pem -pubout -out registry-public-key-2026.pem
   ```

2. 将 private key 移入加密离线存储，至少保留两份受控备份；记录 owner、创建时间、stable lowercase kebab-case `keyId`、public-key fingerprint 与轮换/吊销流程。
3. 只把 `registry-public-key-2026.pem` 的 SPKI public key 和稳定 `keyId` 注入 `src/main/services/registry-update-service.ts` 的 `REGISTRY_TRUSTED_PUBLIC_KEYS`。
4. 在离线机对 exact bundle bytes 签名：

   ```powershell
   node scripts/sign-registry-bundle.cjs <bundle.json> <private-key.pem> <key-id>
   ```

5. 将输出的 `bundleSha256`、`bundleSize`、`signatureAlgorithm`、`keyId`、`signature` 合入 manifest，不重新格式化或改写已签名 bundle。
6. 搜索 staged/tracked files，确认没有 private key marker 或 private PEM；随后运行 production 门禁：

   ```powershell
   npm.cmd run release:preflight
   ```

通过标准：production preflight 无 error；package/CI/repository 中不存在 private key；应用内只有经过 fingerprint 核对的 SPKI public key。若 `REGISTRY_TRUSTED_PUBLIC_KEYS` 仍为空，production preflight 必须 fail-closed，这正是预期行为。

## 5. Windows 三种产物

1. 清空/归档旧 `release/` 证据后执行：

   ```powershell
   npm.cmd run pack:win:all
   ```

2. 确认至少生成：

   - `CCB-Portable-1.5.0.exe`
   - `CCB-Setup-1.5.0.exe`
   - `CCB-1.5.0-win.zip`（若 electron-builder 最终命名略有差异，记录实际名称并确认含 `1.5.0`）

3. 对所有产物执行 `Get-FileHash -Algorithm SHA256 <path>` 并保存结果。
4. 分别验证：

   - Installer：自定义安装目录、Desktop/Start Menu shortcut、首次启动、覆盖升级、卸载、卸载后用户 `.ccb` 是否按设计保留。
   - Portable：从只读以外的独立目录启动，首次启动和二次启动均正常，不污染 Installer 目录。
   - ZIP：解压到全新目录启动，不从压缩包内直接运行，不混用旧文件。

通过标准：三类 artifacts 均可启动，About 显示 `1.5.0`，名称保持 `CCB / Claude Code Butler`，shortcut 与卸载行为符合预期。

## 6. 进程与端口安全操作

启动或切换安装形态前先检查相关 PID，不得结束系统中全部 Node/Electron 进程。

```powershell
Get-CimInstance Win32_Process | Where-Object {
  $_.Name -match '^(CCB|electron)\.exe$' -and $_.CommandLine -like '*ClaudeCodeButler*'
} | Select-Object ProcessId, Name, CommandLine

Get-NetTCPConnection -State Listen | Select-Object LocalAddress, LocalPort, OwningProcess
```

只终止已经核对 command line/path 的具体 PID：

- PowerShell / CMD：`taskkill /f /pid <PID>`
- Git Bash：`taskkill //f //pid <PID>`

禁止执行 `taskkill /f /im node.exe`、`taskkill //f //im node.exe` 或类似的全局进程清理。

## 7. Claude Code 核心业务回归

按下列顺序逐项执行，任一步失败都保留现场和日志，不继续修改同一份 fixture：

1. 扫描：旧 `.ccb/claude-configs` 中全部配置可见；不会静默创建 `.ccb/workspaces/claude-code`。
2. 编辑：分别编辑 JSON 与 Markdown 配置，验证格式化、validation、保存和重新打开。
3. 激活：切换两个 provider/config，确认目标 settings 写入正确且 UI 状态同步。
4. Backup/restore：编辑前备份存在；恢复指定版本后内容、metadata 与激活状态正确。
5. MCP：global/project server 的新增、编辑、enable/disable、import/export 与可用性验证。
6. Agent：新增、编辑、删除、重新扫描和持久化。
7. Skill：新增、编辑、删除、重新扫描和持久化。
8. Managed Mode：记录原 provider/settings；enable、切换 provider、disable；退出后确认原配置准确恢复，无旧 backup 二次覆盖。

通过标准：所有原有 Claude 数据保持兼容，失败操作不产生部分写入，backup/restore 可验证，Managed Mode disable 后 provider 恢复准确。

## 8. Artifact-specific template

建议先复制一份 `settings.json`，分别覆盖以下场景：

1. Legacy migration：在旧版设置中保存一个真实自定义 global template，升级后确认迁移为 `claude-code/user-settings` 的 `USER_OVERRIDE`；旧内置默认值不得被迁移。
2. Source：切换 artifact selector，分别确认 `USER_OVERRIDE`、`REGISTRY`、`EMBEDDED` source tag 与实际内容一致。
3. Validation：尝试空/合法模板、含 NUL、超过 `64 KiB` 或不符合 codec 的模板；无效输入必须拒绝且不修改原值。
4. Diff：准备短模板和超过 1000 行的模板，确认 bounded diff 可读、Settings 不冻结。
5. Save/remove：保存 override 后切换字体等普通设置，override 不得被 stale store 覆盖；移除 override 后回退到 registry 或 embedded，重新启动也不得由 legacy 字段复活。
6. New config preload：打开新建 Claude config，确认 effective template 预填；立即输入草稿，迟到 IPC response 不得覆盖用户输入。
7. Registry lifecycle：安装含新 template 的 registry、rollback、再安装移除 `defaultTemplate` 的版本；user override 始终优先，移除 override 后仍有 embedded fallback。

## 9. Signed registry release candidate

使用隔离的 staging origin/fixture 依次执行并记录 UI status、日志和 registry storage hash：

1. Valid：正确 key、signature、SHA-256、size、version 和 schema，用户确认后安装成功。
2. Tampered bundle：签名后修改任意一个 byte，必须 signature mismatch 且不安装。
3. Tampered manifest：修改 size/hash/version 之一，必须 fail-closed。
4. Unknown key：使用未固定的 `keyId`，manifest check 必须直接 `CHECK_FAILED`，不得显示虚假的 `UPDATE_AVAILABLE`。
5. Downgrade：低于 installed version 的 bundle 必须拒绝。
6. Rollback：安装 RC 后回退 last-known-good，内容与 hash 精确恢复；user template override 不变化。
7. Network：仅自动获取小型 manifest；完整 bundle 只能在用户明确确认后下载。

## 10. Electron runtime security

1. 在任意可渲染 Markdown/链接位置点击 `http://`、`https://`、`file://` 与自定义 scheme，确认不能在 CCB 内创建新窗口。
2. 尝试触发跨 document navigation，当前页面必须保持；Settings 内 hash navigation 仍应可用。
3. 打开 DevTools 仅用于此验收，确认 renderer 中没有 Node.js globals，preload 只暴露预期 API。
4. 检查 Console：不得出现 Ant Design `destroyOnClose` deprecation warning、未处理 Promise rejection 或 CSP/sandbox 降级错误。

通过标准：new-window 和外部/cross-document navigation 全部 fail-closed，合法同 document hash navigation 正常，核心业务 IPC 不受影响。

## 11. 性能验收：三轮中位数

保持 fixture、power mode、安装形态和后台负载一致。每轮完全退出并按具体 PID 确认进程结束；cold start 不清空用户数据。Portable 因自解压机制单独记录，不与 Installer/ZIP 混算。

每一轮执行：

1. Cold start：记录点击/进程创建到主界面 interactive 的时间；无需打开 DevTools，导出 JSON 后从 `rendererTimings` 中读取 `name = ccb-app-init-duration` 条目的 `durationMs`。`ccb-app-init-start` 与 `ccb-app-interactive` 两个 MARK 可用于核对边界。
2. Idle：进入主界面后不操作 60 秒，在 `Settings -> About -> Performance Snapshot` 导出 JSON。
3. Tray hidden：隐藏到 tray 后等待 60 秒。应用内导出需要先恢复窗口，因此恢复后立即导出，并把这份样本标记为“包含恢复扰动”；若需要纯 hidden CPU/memory，同时用 Task Manager、Performance Monitor 或等效 OS 工具记录第 60 秒样本，不要把两种口径混在同一 median。
4. CPU/memory：从 JSON 记录 `totalWorkingSetKb`、每类 process `cpuPercent`、working set 与 peak working set；确认 `rendererTimings` 最多 3 项且只含上述 whitelist entries。
5. Watcher/scan：直接从 JSON 读取 `runtimeMetrics.activeWatcherCount`、`watchedDirectoryCount`、`watchedEntryCount`，以及 `lastConfigScan.completedAt/durationMs/filesVisited/configsLoaded/success`；`lastConfigScan = null` 表示尚未完成配置扫描，不能按 0 ms 计入。确认 watcher counts 不随 hide/show 或页面切换累积，并核对 scan 时间与本轮操作一致。
6. 对三轮分别保存 raw JSON，按 PERF-01 至 PERF-07 计算 median，不删除异常值；异常值单独解释。

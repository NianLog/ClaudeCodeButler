# Agent Note: 先完成 1.5.1，再做可解释、可恢复的配置管理

Status: proposed
Scope: src/shared/tool-registry.ts, src/main/services/**, src/renderer/src/components/**
Last-verified: 2026-10-25


## Problem

多工具用户需要确认配置是否生效、来自哪里，以及切换失败后如何恢复。继续增加配置入口不能直接解决这些问题。CLI 自身的配置、认证和资源管理也在变化，CCB 不能把一次文件写入成功等同于工具运行成功。

这份路线已获用户认可，但功能尚未实施。先完成 1.5.1 的 A/B/C 修复与候选验收，继续遵守“不发布”；1.6 才进入功能交付。1.5.1 的门禁与证据归属见[受支持运行时与正式发布门禁](../../implemented/process/2026-10-19-supported-runtime-and-release-gates.md)。不移动旧用户数据，不建立第二套配置持久化。

## Proposal

1.6 优先支持 Claude Code、Codex 的 Windows/WSL 场景，围绕“发现问题 → 解释来源 → 修改预览 → 核对结果 → 恢复”组织现有能力，复用 registry、配置集、备份和路径 facade。

| 顺序 | 用户任务 | 边界 |
| --- | --- | --- |
| P0 | 配置诊断：识别工具版本、运行环境、配置来源与优先级，解释被覆盖或被组织策略限制的字段 | 无法读取实际运行状态时标为未验证；不能用进程存活或无错误日志推算健康分 |
| P0 | 可恢复修改：展示字段差异、检查写入前冲突、备份与恢复，并核对工具能够读取的结果 | 多文件修改不宣称事务；结果未知先核对，不自动重发可能收费的操作 |
| P0 | 项目启动与环境切换：优先使用 CLI 原生单次启动配置或 Profile，减少全局配置干扰 | 先识别版本与能力，不假设所有 CLI 支持同一种隔离方式 |
| P1 | MCP 按工具与作用域同步，只预览和修改 MCP 子树 | 不用旧配置快照覆盖 OAuth 刷新结果或无关设置 |
| P1 | Skill 的来源、版本、兼容范围与安全更新 | 签名证明来源，不能证明内容安全；沿用 C 批覆盖保护，不自动执行脚本 |
| P1 | 登录方式、计费来源与使用情况的可见性 | 估算不等于账单或真实剩余额度；告警不等于全局硬预算 |
| P2 | Hooks 模板与团队配置包 | Hooks 预览不能承诺任意命令安全；团队包排除个人密钥，组织签发与 CCB 官方签发分开建模 |

CCB 自有凭据优先考虑系统安全存储，但 CLI 必须读取明文的字段要明确告知。无感采集、云端密钥托管、通用聊天工作台、多代理会话编排、公共市场、自动最低价路由和全平台深度适配不进入本阶段。

## Evidence and uncertainty

以下资料核对日期为 2026-10-20。调研包括官方文档、维护者发布记录和原始问题，未进行 CCB 用户访谈，不能把外部用户问题当作 CCB 需求量或付费意愿的测量结果。

- [Claude Code configuration](https://code.claude.com/docs/en/configuration) 已有多层配置；诊断需要说明来源和优先级，而不是重复提供文件编辑器。[环境变量](https://code.claude.com/docs/en/env-vars)影响认证与计费选择，部分变化需重启进程。
- [Codex advanced configuration](https://developers.openai.com/codex/config-advanced/) 的 0.134.0+ Profile 使用 `<name>.config.toml` 和 `--profile`；旧 `[profiles.*]` 不能继续作为通用格式。未来实施必须按实际版本确认，不能直接迁移用户现有配置。[组织策略](https://developers.openai.com/codex/enterprise/managed-configuration/)已有原生约束能力。
- [CC Switch v4.0.16](https://github.com/farion1231/cc-switch/releases/tag/v4.0.16) 表明托盘、认证保留和代理稳定性也在持续改进；仅增加服务商切换不足以形成明确优势。历史[配置覆盖问题](https://github.com/farion1231/cc-switch/issues/4699)只用作失败场景参考，不代表当前版本仍存在该问题。
- [Agent Skills specification](https://agentskills.io/specification)支持资源共享，但各 CLI 的安装位置、权限和运行语义仍需分别验证。[Gemini CLI 文档](https://geminicli.com/docs/)显示部分用户层级已迁移至 Antigravity CLI，不能把 Gemini 适配器的历史存在当成未来需求稳定。
- [Stack Overflow 2026 AI 调查](https://survey.stackoverflow.co/2026/ai)可用于观察信任与质量诉求，不能据此推算 CCB 留存、定价或市场份额。

未来 6–12 个月 CLI 原生配置能力继续完善、格式和认证持续变化是高置信度判断；12–24 个月资源格式趋同但运行和权限仍有差异是中等置信度推断。团队治理的商业价值尚待访谈，不承诺定价、收入或市场规模。

## Follow-up

1. 1.5.1 由发布门禁笔记持续记录实际通过、失败和外部阻塞；未完成的验收不得勾选，未发布不得改写成已发布。
2. 1.6 开工前访谈建议 12 人：多 CLI 用户、Windows 新用户和团队负责人各 4 人；观察最近一次配置失败、项目切换和 MCP 安装，而不是只问想要什么功能。
3. 先制作诊断与恢复的少量高保真主界面样稿，再决定实现批次。每项功能落地时另写有明确边界与验证方式的实施笔记，本路线继续保持 proposed，直到承诺范围实际完成或经用户调整。
4. 主要指标是“可验证的配置任务成功率”和“从诊断到恢复的时间”。已有 CLI 与账户下 5 分钟接入、10 个任务至少 8 个无需协助完成是待验证目标，不是已取得成绩。研究数据由用户主动导出，默认不上传配置、密钥或使用记录。

## Alternatives considered

- 立即把诊断、项目工作区和团队功能并入 1.5.1，可以快速展示新能力，但会扩大 Electron 升级和安全修复的回归范围；本次选择先完成修复候选。
- 继续堆叠更多 CLI 和服务商入口，可以增加覆盖面，但兼容与权限语义不同，缺乏真实用户需求验证；先把两个主要工具的诊断与恢复做完整。
- 建立独立的工作区数据库便于隔离，但会形成新的持久化和迁移负担；优先复用现有配置集、备份和 CLI 原生启动能力。
- 自动最便宜路由有费用吸引力，但工具兼容、账单真实性、失败重试与结果未知会影响可靠性；先提供可核对的信息，不承诺自动省钱。

## Acceptance criteria

- 1.5.1 修复与发布准备独立验收，保留旧配置路径和数据格式，正式发布仍需用户授权及现有门禁。
- 1.6 实施前取得上述任务观察证据，并明确支持的工具版本、环境和失败后的恢复步骤。
- 诊断能区分已验证、推断和无法读取；组织策略、认证来源、未生效原因和重启要求不被隐藏。
- 修改前预览差异并检测外部变化，验证失败保留原数据；实际支持范围内可恢复，不声称跨进程或断电事务。
- 不新增默认遥测，不采集密钥，不把费用估算当账单，不把签名当作 Skill 内容安全结论。

## Risks

版本识别、WSL 边界和组织策略可能限制有效配置的确认；必须允许明确的“无法验证”，不能以一个总分掩盖。访谈样本和指标目标尚未验证，P1/P2 优先级可以随证据调整。凭据安全存储不能替代 CLI 对明文文件的要求。

新建时检索现有三篇笔记：发布流程笔记与本路线部分重叠，双方互链；两篇 A/C 缺陷笔记描述已经实施的修复，不被本路线取代。没有过时提案需要删除或归档。旧 `docs/1.5.0/11-*` 与 `13-*` 保留为历史方案；新实施须复核当时的 CLI 格式，不机械沿用。
